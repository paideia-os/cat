## What landed

- `manifest.pdxsig` — dual-signed package manifest per §D4.
  Sections §1..§5 carry real values (identity + caps.decl hash +
  deps.list ref + sha2-256 content hashes over the shipped tree +
  declared output schemas). Sections §6 (author signature) and §7
  (root signature) carry `PENDING` in place of the 3293-byte
  ML-DSA-65 signature bytes; §8 documents the refusal invariant.
- `deps.list` — required by plan.md §9.1; empty at v1.0 with a
  header explaining why every libpdx-* consumer site is an in-tree
  stub and what the migration to v1.1 looks like.
- `cat.pdxdoc` — long-form doc file per invariant I7 §2 in
  `.SECTION` / `.META` / `.CODE` / `.POSIX-DIFF` format. First
  `.pdxdoc` to ship in R49/R50 — sets the shape the doc.M1-002
  parser reads.
- `CHANGELOG.md` — v1.0.0 section rolling up M1..M5. Documents the
  substrate posture and the signature refusal witness.
- STATUS.md — M5-001 row flipped to LANDED.

## Design decisions

**The manifest text form is diffable, not authoritative.** The
on-wire `manifest.pdxsig` is a binary-encoded ML-DSA-65 signature
envelope produced by `paideia-as release --sign` per plan.md §9.3.
The file committed to the repo is the human-review-friendly source
form the signing bot re-emits into binary. This is why the text form
carries sha2-256 hashes (available at HEAD via `sha256sum`) with a
note that the on-wire form carries sha3-256 (per §D4). No reviewer
disagreement is possible between the two forms because both are
generated from the same source-tree snapshot at the git tag.

**Signature bytes are `PENDING` — a stub, not a hole.** Two
substrate gates block real signatures: (a) `paideia-as v0.33-crypto`
tag with the `ml_dsa_65_{sign,verify}` intrinsic + `sha3_256`
primitive, and (b) `T-INFRA-002` in the paideia-os meta repo
(signing bot host + `paideia_root_pk` provisioning). The
`PENDING` bytes make the manifest a valid v1.0 shape that fails
verification with a specific, expected error class — signature
substrate not landed. `pkg install cat` refuses with exit 4 (cap
denied per I4). The refusal is an invariant of the two-key policy;
it is not a reviewer discretion. This mirrors how M2-M4 shipped
with test-seedable source-side stubs standing in for kernel
substrates: the shape is real, the payload will be regenerated by
the substrate when it lands.

**`.pdxdoc` format shape — first-of-N.** cat is the first R50 tool
to ship `.pdxdoc`, so the concrete layout here is the working
reference for pkg / shell / doc / ls / cp / mv / rm / mkdir / grep /
find / less. Format goals: (1) line-oriented so the doc.M1-002
parser is a byte-scanner without a lexer, (2) `.SECTION` /
`.END-SECTION` markers to make PdxDocEntry emission (doc.M3-001)
straightforward — one record per section, (3) `.XREF` for the
cross-reference graph (doc.M3-002 PdxDocReference[] schema),
(4) `.POSIX-DIFF` callouts to make the `--differences-from-posix`
help section fall out of the same file rather than requiring a
second doc. Details tunable at doc.M1-002 refinement time; every
`.pdxdoc` shipped by the R49/R50 wave can migrate together if
doc.M1-002 lands a stricter shape.

**`deps.list` is empty on purpose.** The six libpdx-* libraries cat
consumes today are in-tree stubs, not installed shared libraries.
An `entries:` block listing them here would create a fake install
closure that would refuse at `pkg install cat` time because those
packages do not exist yet in `pkgs.paideia-os`. The empty deps.list
correctly reflects the closure at v1.0 and reserves the header note
as the migration ledger for the v1.1 dep set.

**Content-hash scope.** The `content_hashes` block covers LICENSE
+ all `src/*.pdx` — the files that end up in the installed pkg
under `/pkgs/cat-1.0.0/bin/` (LICENSE) and `/pkgs/cat-1.0.0/src/`
(source, for reproducibility from-source builds). It intentionally
does NOT cover `tests/*.pdx`, `.plans/*.md`, `design/*.md`,
`README.md`, `STATUS.md`, `CHANGELOG.md`, `MIRROR.md`, or the
`.pdxdoc` file — those are development artifacts, not runtime
inputs. The `.pdxdoc` file's hash lands in a companion entry when
doc.M5-002 wires `pkg install <tool>` to copy the .pdxdoc into
`/system/doc/<tool>.pdxdoc`, which requires a schema field the
manifest.pdxsig format does not yet carry. That is a coordinated
follow-up across cat.v1.1 + doc.v1.1 + pkg.v1.1.

## Compliance

M5 does not add source or test `.pdx` files; the four artifacts
(`manifest.pdxsig`, `deps.list`, `cat.pdxdoc`, `CHANGELOG.md`) are
docs/manifests. No paideia-as conformance rules apply to text
artifacts. The `.pdxdoc` format is deliberately NOT `.pdx`; it is
a data file consumed by the `doc` tool at runtime.
